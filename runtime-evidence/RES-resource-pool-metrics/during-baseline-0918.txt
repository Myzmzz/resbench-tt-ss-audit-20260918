## 补充（2026-09-18 09:2x UTC，同一 Prometheus，kube-state-metrics + cAdvisor）
- CPU limit/request：train-ticket 46 个 ts-* 容器 request 10m、limit 1.5 核；业务库 tsdb-mysql 的 mysql 容器 request 100m / limit 500m、内存 256Mi/1Gi；xenon 容器 limit 100m / 256Mi（选主与健康检查进程）；nacos 容器 request 500m。
  sock-shop：catalogue、payment limit 200m；user、front-end、queue-master、carts、shipping limit 300m；orders limit 500m；request 均约 100m。
- 基线（1 QPS）下 tsdb 三个 MySQL Pod 的 CPU 用量约 0.01 核，网关三副本各约 0.03 核、节流 <0.5%——train-ticket 的数据库与网关在基线负载下都不是瓶颈；上表 train-ticket 的高节流 Pod 都是 09:07–09:10 刚重启的服务，节流来自 JVM 启动期（limit 1.5 核），不是稳态。
- sock-shop 各 Pod 在压测前已稳定运行数小时，carts 30% / orders 21% 的节流发生在 5 个虚拟用户的稳态负载下（limit 300m / 500m）。
- 注意：本环境 cAdvisor 只有 Pod 级 cgroup（cgroup v2 + cri-dockerd，无 container 标签），所以内存/CPU 都是 Pod 级数值；对单容器 Pod 等同于容器数值，mysql 等多容器 Pod 是容器之和。
